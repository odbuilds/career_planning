# Nesto — Project Summary

## What It Is

Nesto is a Canadian online mortgage lender. Their SDRs (Sales Development Representatives) make outbound calls under the alias **CompareMortgages** (English) and **MonMeilleurTaux** (French). The project automatically scores how well each SDR follows a defined call guidance script, pushes those scores to BigQuery, and surfaces them in a Looker dashboard so sales leaders can coach agents with real data.

**Full pipeline:** Raw audio → Transcription (Speechmatics) → HumanFirst (LLM scoring) → BigQuery → Looker Dashboard

## Scoring Criteria

Each call scored 0 or 1 across 8 criteria:

| Key | Question |
|-----|----------|
| `agent_name` | Did the agent introduce themselves by name? |
| `user_name` | Did the agent greet the user by name? |
| `calling_organization` | Did the agent explicitly mention CompareMortgages or MonMeilleurTaux? |
| `reason_for_call` | Did the agent mention the inquiry and that it was started on the website? |
| `mortgage_need` | Did the agent understand the user's mortgage situation? |
| `mortgage_timeframe` | Did the agent verify the user's likely mortgage timeframe? |
| `credit_score` | Did the agent ask whether the user knew their credit score? |
| `next_steps` | Did the agent clearly communicate next steps? |

## Airflow Architecture

Three independent DAGs with BigQuery as the shared state store. Each DAG tracks progress via a `processed_status` field (`UNPROCESSED → INGESTED → PROCESSED`).

### DAG 1 — Transcription *(TBD at handover)*
GCS audio bucket → Speechmatics transcription → HF-compatible CSV → BQ `conversations` table. Deduplication by tracking already-transcribed filenames.

### DAG 2 — Ingestion
Reads `UNPROCESSED` rows from BQ → batches into Pandas DataFrame → uploads timestamped CSV to HumanFirst conversation set → polls trigger until complete → updates BQ status to `INGESTED`.

Key details:
- Batch size configurable via Airflow Variable (`INGESTION_BATCH_SIZE`)
- Validates conversation set exists before pulling any data
- Enforces rolling window — deletes oldest file if convo-set exceeds file limit
- Trigger polling: checks `COMPLETED`, `FAILED`, or `CANCELLED` status

### DAG 3 — Insight
Triggers HumanFirst pipelines on new files, exports results, pivots key-value output into columnar BQ schema, upserts to `insights` table.

Key details:
- Incremental cursor: finds files newer than the last filename written to BQ
- Supports multiple pipelines sequentially (e.g. separate pipelines for calls vs. chats)
- Retry logic: 3 retries on failed/cancelled triggers before DAG fails
- Atomic upsert: all pipelines must succeed — partial results are never written
- Delete-before-insert on `conversation_id` to prevent duplicates

## Project Challenges & Solutions

**Transcription accuracy killing scores**
Agent names were mis-transcribed, causing the name introduction criterion to score 0 incorrectly.
*Solution:* Speechmatics content enrichment with known agent and company names. Standard → Advanced transcription upgrade. A prompt-level name correction was available as a fallback but noted as a blunt instrument.

**French language support**
Early scoring only handled English. French calls scored incorrectly due to different company alias (MonMeilleurTaux).
*Solution:* Extended prompt and content enrichment to handle French equivalents explicitly.

**Prompt too strict**
Initial grading failed calls where transcription noise made criteria appear unmet.
*Solution:* Iteratively loosened the prompt to read between the lines of likely mis-transcriptions.

**Validating prompt quality**
No ground truth to verify LLM scoring was accurate.
*Solution:* Manual human evaluation of 50 randomly sampled English calls before scaling to 3,600+.

**Fuzzy 4-criteria prompt didn't scale**
The original scoring was inconsistently applied across campaigns and languages.
*Solution:* Rebuilt as 8 explicit binary questions with precise definitions and edge case guidance baked directly into the prompt.

**Manual process didn't scale**
Running the pipeline manually each week was not viable for ongoing cadences.
*Solution:* Airflow DAG design with BigQuery as state store, rolling window management, trigger polling, and retry logic for full automation.

**Duplicate data on reruns**
Re-processing calls could produce duplicate BQ rows.
*Solution:* Delete-before-insert pattern on `conversation_id` in both the BQ script and Insight DAG.

**Rolling window creating a processing gap**
The convo-set only retains the N most recent files. If the Insight DAG fell behind, deleted files could never be processed — insights for those calls permanently lost.
*Solution:* The two DAGs must run at compatible frequencies. The system accepts this as a design trade-off: if the Insight DAG stays in sync, no data is lost; if it falls significantly behind during downtime or repeated failures, there is no recovery path for the deleted files.

**Empty files blocking the insight cursor**
Files that produced zero insights (bad audio, too short) never appeared in BQ. The DAG would repeatedly attempt to process them, blocking all newer files.
*Solution:* Cursor advances based on time-ordered filename position, not per-file completeness. All files newer than the last written filename are processed in a single batch — empty files are included, produce nothing, and the cursor moves past them once any newer file writes successfully.

**On-prem API endpoint**
Nesto's HumanFirst instance was on-prem, not cloud — the standard API docs didn't apply.
*Solution:* Flagged as a follow-up item; custom endpoint configuration required but not fully resolved within the engagement scope.

## BQ Schema

**`conversations` table** — raw transcribed calls with processing status

| Field | Type | Notes |
|-------|------|-------|
| `conversation_id` | STRING | |
| `conv_created_at` | TIMESTAMP | |
| `utterance` | STRING | |
| `speaker` | STRING | |
| `agent_id` | STRING | |
| `processed_status` | STRING | UNPROCESSED / INGESTED / PROCESSED |
| `hf_conv_filename` | STRING | e.g. `file-2024111T0000` |
| + campaign metadata | | member_level, intent, campaign_nm, sdr_success_ind, url |

**`insights` table** — pivoted pipeline scores, joined to conversations on `conversation_id`

| Field | Type | Notes |
|-------|------|-------|
| `conversation_id` | STRING | Foreign key to conversations table |
| `agent_name` | INTEGER | 0/1 |
| `user_name` | INTEGER | 0/1 |
| `calling_organization` | INTEGER | 0/1 |
| `reason_for_call` | INTEGER | 0/1 |
| `mortgage_need` | INTEGER | 0/1 |
| `mortgage_timeframe` | INTEGER | 0/1 |
| `credit_score` | INTEGER | 0/1 |
| `next_steps` | INTEGER | 0/1 |
| + reasoning fields | STRING | One per criterion |

**Join query used in Looker:**
```sql
SELECT
  sdr_calls.*,
  insights.agent_name,
  insights.user_name,
  insights.calling_organization,
  insights.reason_for_call,
  insights.mortgage_need,
  insights.mortgage_timeframe,
  insights.credit_score,
  insights.next_steps
FROM `poc.insights_table` AS insights
LEFT JOIN `poc.tbl_sdr_calls_enriched` AS sdr_calls
ON insights.conversation_id = sdr_calls.call_id
```

## Prompt Design

The scoring prompt takes a raw call transcript and returns structured key-value output — one score (0 or 1) and one reasoning string per criterion. No markdown in the output, plain text template enforced, making it reliable to parse downstream.

A second **coaching report prompt** aggregates scores across multiple calls for a single agent and produces written guidance — strengths, areas for improvement, and specific recommended script changes with before/after examples.

The prompt design philosophy throughout was:
- Binary scoring only (no partial credit) to keep downstream aggregation simple
- Criteria written as yes/no questions with explicit edge case guidance inline
- Loose enough to handle transcription noise, strict enough to be meaningful
- Language-agnostic where possible (both EN/FR handled in a single prompt)
