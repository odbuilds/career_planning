## Discovery Methodology (how to identify automation opportunities)
The hardest part of this role — be ready to articulate a process, not just "I ask what people want."

**Four-stage approach:**
1. **Stakeholder interviews** — two questions per team: "What do you do repeatedly that you wish you didn't?" (automation) and "What do you always mean to do but never get to?" (augmentation)
2. **Time/effort mapping** — get rough hour estimates per week per person. A 2hr/week task × 10 people = 20hr/week problem. Target: manual data entry, copy-paste between tools, report generation, status-chasing emails
3. **Data availability audit** — before building anything, understand where data lives and what shape it's in. Structured CRM = quick win. PDFs in inboxes = hard. This determines feasibility, not just priority
4. **ROI × effort prioritisation** — score on impact (time saved × frequency × people affected) vs effort (data readiness × integration complexity). Quick wins first to build trust and mandate

- **Finance:** invoice processing, expense categorisation, reporting
- **Ops:** contractor onboarding comms, contract status tracking
- **Product:** user feedback synthesis, support ticket clustering

## Experimentation Philosophy

Every automation is an experiment. This sits uncomfortably with some people because it implies things might fail — but that's the point. Set up with a hypothesis, track data from day one, and maximise learning regardless of outcome.

### The infrastructure this requires:

**1. Hypothesis card (pre-build)**
- What problem are we solving? (in the stakeholder's words)
- What does success look like in numbers? (hours saved, error rate, volume)
- What's the measurement window?

**2. Baseline first, always**
Before any automation: capture time estimates, error rates, current tool/process. Even rough numbers beat no numbers.

**3. Simple instrumentation on every workflow**
- Run count (is it being used?)
- Failure/error rate (is it breaking silently?)
- Time-to-complete vs baseline
- In n8n: execution logs are built in; aggregate into a lightweight experiment registry (Notion table or similar)

**4. Monthly review cadence**
30-minute forcing function with department head: confirm/reject hypothesis, kill/double-down/extend.

**5. Learning artifact**
One paragraph per experiment at close: what we built, what we expected, what happened, why. This compounds — six months in you have a pattern library of what works in this org.

**Key reframe:** An experiment that proves something doesn't work is still a success — faster and cheaper than building the wrong thing at scale.

## n8n Versioning Approach

Workflows are code — treat them like code.

- **Built-in version history:** good as a safety net (restore last 20 saves), not a versioning strategy
- **Git + export script:** n8n exposes all workflows via API (`GET /api/v1/workflows/:id`). A nightly script pulls all workflows as JSON and commits to a Git repo. ~30 lines of Python + a cron job. Full history, diffable, restorable.
- **n8n native source control:** available on Enterprise/Cloud plans — connects directly to a Git repo with dev/staging/prod promotion. Worth asking which plan they're on.

**The discipline that matters more than the tooling:**
- Never edit production directly (dev instance or staging duplicate)
- Export to Git before touching any workflow a department depends on
- Include version + date in the workflow's description field

## What "Building Internal Infrastructure" Actually Means

Three layers that build on each other:

**Layer 1 — The plumbing (first 60–90 days)**
Single data connectivity layer (Slack, Salesforce, email, internal tools), n8n properly hosted/monitored, credential management, error alerting. Invisible when it works; makes everything else fast.

**Layer 2 — The workflows (ongoing)**
Modular, documented, versioned automations that run without babysitting. Not dependent on the builder to operate.

**Layer 3 — The memory system (strategic)**
Vector DB + ingestion pipeline + retrieval hooks. Context travels across departments. Institutional knowledge gets captured. The system compounds over time.

**Interview framing:** Lead with the infrastructure question, not the automations: *"Before I build anything, I want to understand where your data lives and whether it's connectable — that determines what's possible."*
